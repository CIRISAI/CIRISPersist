## 1. Design: one rule set, two codecs (the "vouched" door)

`put_statement` → `group::put_group_statement`. The call comes after `admit_row` and `check_composer_target`, and before the key-plane and attestation paths. It does this:

1. `payloads::check` against the family's table. The header id is mapped to the template by `namespace_match::family_id`.
2. The statement is mapped onto the typed record it replaces (`record_of_roster`, `membership_of`).
3. The voices are every held statement of the row id plus the offered one, one per `iss`:
   - the primary is the group key's own voice if it spoke, else the smallest iss;
   - the others become `RosterCosignature`s;
   - the signature columns hold each voice's composite signature in base64 (the "marker").
4. The JSON form's own door runs **unchanged** (`put_family`, `put_community`, `put_{family,community}_membership_{revocation,widening}`) inside a task-local `Vouch`. The Vouch holds the record's envelope hash, signer → marker, and the change envelope (for a later version).
5. The result:
   - `Ok` → the voice is stored → `Row`;
   - a structurally noted shortfall, or `membership_founding_member_unsigned` → the voice is stored → `Pending`;
   - any other `Err` → the voice is not stored.

**Later versions.** `refs.head` names the predecessor statement. `prev_head_digest` is the predecessor's typed `persist_row_hash`, re-derived by walking the held chain down to v1 (the hash is a pure function of the statements).

The supersede proof is built as follows:

- `prior` is that hash;
- `change_envelope` is `build_membership_change_envelope(..)` over this node's held state;
- `quorum_signatures` is empty, because the vouch supplies the signers.

From there K1's route decides Extends or Tip.

An unheld predecessor, or a later version of an unheld group, waits: `WithdrawsTargetUnheld`, retryable. The version must be the predecessor's + 1, and 1 when there is no `refs.head`.

## 9. Added scope: the roster is the members common to all tips (CC 2.7.8)

The CC text (`CIRISConstitution/constitution/part_2_the_grammar.md:1374`): "Two versions of one head wait as tips. The roster is then the members common to all tips, until a version naming the tips makes one head again." RULINGS.md has only "a fork is held as a tip". K1.md §6.1 ruled this read is T1's.

### `edition2::group::forked_tip_members(dir, cohort, group, head_hash) -> Result<Option<BTreeSet<String>>, Error>`

It builds the held version graph:

- the roots are the head, every version in `federation_group_versions` (its snapshot's `persist_row_hash`), and `""` (a version naming none);
- a K1 tip joins the graph when its `prev_head_digest` names a node already in it (iterated to a fixpoint);
- a tip waiting on an unheld version is not in the graph and narrows nothing.

The answer:

- the leaves are the head and every in-graph tip that no other in-graph tip names;
- with no in-graph tip it returns `None` (one head);
- otherwise it returns the intersection of the leaf tips' listed members (from the snapshot, `family` / `community` or bare);
- a directory whose `list_group_tips` is `Unsupported` returns `None`.

### Wired in `federation/mod.rs` (foreign, the roster folds)

The caller keeps only the head's authorized members that are in the set:

- `authorized_family_roster_at`;
- `authorized_community_roster_at`;
- `authorized_community_roster_spans_at`.

These are "the one fold every gate reads", so the narrowing reaches `active_*_members`, `verify_membership_quorum`'s roster, the roster-authority standing and the group prior envelope. A new private helper, `community_forked_tip_members`, uses the record's declared cohort (`affiliation_config::declared_cohort`), because an affiliation's versions are `affiliations`.

### Witnesses (`group_invariants::i3001_i3002_fork_roster_{sqlite,postgres}`)

- **I3001**, overlap, through the door:
  - v1 {a,b,c}; the head v2 {a,b,c} is renamed;
  - a fork v2' {a,b} naming v1 is held as a tip;
  - `active_family_members` goes from {a,b,c} to {a,b}.
- **I3002**, disjoint:
  - w1 {a,b,c,e}; the head w2 {a,b} comes through the door;
  - a tip {c,e} naming w1 empties `active_family_members`.
  - **The disjoint tip is planted through `supersede_group_row` (K1's executor).** The door cannot produce it: the #955 Q2 rule "an amendment never adds a member" is judged against THIS node's head (K1), so no tip can list a member the head lacks. The witness is of the read rule over held tips, not of how they arrived.

### Risks

- **Every roster fold now does one more read** (`list_group_tips`), plus `list_group_versions` when tips exist. It is not memoized in the community roster-read memo.
- **The tip's members are its record's listed members.** A widening or removal plane counted over a tip is not folded per tip; the head's fold is intersected with each tip's record. So a member widened at the head after the fork is outside the common set (fail-closed). This matches the CC: a fork "unlists members and never lists one".
- **No merge.** "A version naming the tips makes one head" is not wired (K1 §6.2: needs `further_heads` in the payload rule). Until one is, a held fork narrows the roster for good. A fork of disjoint members therefore freezes the group: no quorum can be met. K1 makes every tip quorum-verified against the head at admission, so only a quorum of the current roster can cause this.
- **A future-dated read.** `as_of` is not applied to tips: a tip narrows every read from the moment it is held, at any `as_of` (`held_at` is not compared).
- **Recursion.** `forked_tip_members` reads `list_group_tips` / `list_group_versions` only (SQL), never a roster fold. *read-checked* for sqlite's `list_group_tips`; `list_group_versions` is believed to be SQL only.
- **Compile.** It uses `Option::is_none_or` (already used in the crate) and K1's `list_group_tips` and `Error::Unsupported { .. }`.

## 11. v4: a fork heals (CC 2.7.8 merge)

### The text (CC v1.0-rc20, `constitution/part_2_the_grammar.md`)

- **2.7.8**: "Each version names the heads it extends and is counted over their members." And: "Two versions of one head wait as tips. The roster is then the members common to all tips, until a version naming the tips makes one head again."
- **The grammar** (part 2, lines 556, 638, 831, 904, and `manifests/signed_object_v2.cddl:156`): "The head the row is counted over stands in `refs.head` … Further tips stand in `refs.further_heads`, a set."
- **The formal model** (`formal/causal_order/README.md`, `Kernel.RosterHead.voters_is_common`): "a version naming several heads is counted over the members common to them".
- **2.7.3 / 2.7.4** add only that a count is over the members at the head its row names.

So the text does name a resolution, and **no question for CC is needed**. One reading is persist's and is marked as one: a merge that names only SOME of the tips makes one head of those it names, and the tips it does not name remain tips, so the roster stays common across them. The text speaks of "the tips" (all of them); a partial merge is not refused.

### Wired (`edition2::group`)

- **`RosterView.further_heads`** is read from `refs.further_heads`, and `parents()` = head + further.
- **`merge_reading(dir, view, row_id) -> MergeReading { prev, merged }`**. `prev_head_digest` now delegates to it.
  - The held chain behind every parent is loaded with an explicit stack and memo, through every merge's parents, down to v1. An unheld named version waits (`federation_withdraws_target_unheld`).
  - The version must be the greatest named version + 1.
  - `refs.further_heads` without `refs.head` is `edition2_payload_invalid`.
- **The merge's typed `prev_head_digest`** (`chosen_prev`) is the named version that THIS node's lineage holds (the head, or a version in `federation_group_versions`), else `refs.head`'s.
  - So the K1 executor reads a merge as **Extends**, whichever tip this node happened to hold as the head.
  - The same rule re-derives the merge's typed hash in every later chain walk: the superseded head is then in history, and the merged tips are not.
- **The count is the one that is already wired.** `verify_membership_quorum`'s roster is `active_*_members`, which v2 narrows to the members common to all tips. A merge naming every tip is therefore counted over the common members, which is CC's rule.
- **After the merge lands as the head**, the other named tips' typed hashes are dropped from `federation_group_tips`. This uses a new trait method (below). It is idempotent, and it re-runs on any re-put voice, so a crash between the supersede and the drop heals.
- **Writers**: `roster_payload_merging(record, version, head, further, at)` (`roster_payload` = no further), and the fixture `group_fixtures::merge_voices(..)`.

### New trait method (foreign: mod.rs, both backends, double, capsule, conn model)

`FederationDirectory::drop_group_tips(cohort, group_key_id, persist_row_hashes: &[String]) -> Result<(), Error>`.

- The default is `Unsupported`.
- sqlite: one `DELETE` per hash inside a write transaction.
- pg: `DELETE … persist_row_hash = ANY($3)`.
- `directory_double.rs` was regenerated with `scripts/gen_directory_double.py` on my base. **At synthesis, re-run the generator over K1's mod.rs too**, because K1 also regenerated it.
- `directory_capsule.rs`: a `PROXY_UNSUPPORTED_ALLOWLIST` entry with a reason.
- `sqlite_conn_model.rs`: `("drop_group_tips", ConnClass::Write)`.
- **K1's `list_group_tips` has NO `SQLITE_CONN_CLASSES` row** in K1.patch. The gate `every_connection_touching_fn_in_sqlite_rs_is_classified` will name it: add `("list_group_tips", ConnClass::Read)` at synthesis.
